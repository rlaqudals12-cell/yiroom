## 조사 근거 요약 (2026-07-16 실측)

- **타이틀 패턴**: 상위 앱 전원이 `브랜드 + 구분자 + 검색 키워드` 구조. 시장별로 타이틀 자체를 현지 키워드로 교체 (Dressika·ColorMe AI·VividMe 확인).
- **일본**: 랭킹 상위권 전부 무료 진입 — `無料` 명시가 사실상 필수. 살롱의 "토탈 진단"(カラー×骨格×顔タイプ) 수요 대비 앱은 단일 축 위주 = **5축 통합이 빈틈**.
- **중화권(번체)**: 현지 전용 강자 없음. 한국산 Colorlover가 "韓國個人色彩App" 프레임만으로 HK01·Bazaar HK 바이럴 실증 — **`韓國` 키워드 명시 권장**.
- **영어권**: 1위 Style DNA가 전면 구독제 → **"100% free, no subscription"이 즉시 대비되는 차별화**.
- **신뢰 클레임**: 경쟁사는 "정확도 90%"·"전문가 감수"를 전면 배치. 이룸은 검증 안 된 수치 대신 **재현성("같은 사진이면 같은 결과") + 색채학 원리** 서사 사용.

### 표기 결정 (가드레일 적용 노트)

- "진단"은 뷰티 관용어(퍼스널컬러 진단·骨格診断)로만 사용, **피부는 항상 "분석"** + 전체 설명 하단에 비의료 고지 고정.
- 검증 불가 수치(정확도 %·유저 수) 사용 금지. "무료" 단어는 앱 이름 제외, 설명에만.
- 브랜드 표기: ja = `Yiroom`(본문 병기 イルム), zh = `Yiroom`. ⚠️ 최종 확정 필요 (사용자 결정).

### 실기능 정합 감사 (2026-07-16 코드 확인 반영)

- **"사진 한 장" 클레임 수정됨**: 실제 플로우 = 얼굴 셀카 **필수** + 전신 사진 **선택** (`ImageUploadSection.tsx` 확인) → 전 언어 "셀카 한 장으로 **시작**" 프레임으로 교체. 체형은 전신 사진 조건 명시.
- **ja `顔タイプ診断` 삭제**: 일본 협회 상표 계열 시스템(キュート/フレッシュ 등)이며 이룸 미제공 — 사용 금지.
- **ja `骨格診断` 키워드는 유지하되 기대치 주의**: 일본 사용자는 ストレート/ウェーブ/ナチュラル 3타입 판정을 기대. 이룸 체계가 다르므로 **본문에서 구체 타입명 약속 금지** (현재 초안 준수). 일본 사용자 불만 1순위 후보 — 출시 후 리뷰 모니터링 항목.
- **zh "일정 기반 브리핑" 삭제**: 캘린더 연동 기능 없음 → 일반 문구로 교체.
- **"언제든 삭제" 클레임 유지**: 계정 삭제 실재 확인 (`DeleteAccountDialog` + `/api/user/account` + GDPR 삭제 스키마 + 삭제 리마인더 크론). 실기기 스모크에서 동작 재확인만.
- **글로벌(en/zh) "제품 연결" 클레임 타이밍**: 현재 구매 링크가 한국몰 중심 — YesStyle(Awin) 개통 전 글로벌 사용자에겐 체감이 약함. **en/zh 리스팅 공개는 Awin 개통과 맞물리는 것을 권장** (ko 우선 출시 → 글로벌 리스팅 순차 활성화).
- **가상 시착/가상 메이크업 클레임 없음 유지**: 경쟁 앱(VividMe 등)이 제공하나 이룸 VTO=OFF — 스크린샷에서도 암시 금지.

### 심층 감사 2차 (2026-07-16 4에이전트 — 모바일 패리티·i18n·웹 클레임·경쟁 리뷰)

**🔴 리스팅 공개 범위 확정: ko 단독 선공개.** 모바일 앱(=Play 제출물)은 i18n 소비자 0 — 화면의 88%가 한국어 하드코딩, ja/zh 사전 파일 자체가 없고 언어 설정 메뉴도 없음. AI 결과·브리핑도 `locale:'ko'` 하드코딩. en/ja/zh 리스팅으로 설치한 유저는 100% 한국어 앱을 받음 = 1성 리뷰 + "오해 소지 리스팅" 정책 리스크. **en/ja/zh 초안은 모바일 i18n 배선 후 활성화** (Awin 조건보다 이게 선행).

**🔴 제출 전 수리 필수 (Play 정책·기능 자체 문제 — 리스팅 문구와 무관)**

1. **계정 삭제 무음 실패 가능성**: 모바일은 웹 `/api/user/account`가 아닌 `supabase.rpc('request_account_deletion')` 호출인데 이 RPC의 SQL 정의가 저장소에 없음. 폴백(privacy.tsx:180-192)은 Clerk 환경에서 user null → 0행 업데이트 → 에러 없이 "삭제 요청 완료" 표시(거짓 성공). Play 데이터 안전 신고와 실동작 불일치 = 정책 리스크. prod RPC gap-apply + 실기기 삭제 검증 필수.
2. **스캔 Gemini 키 구조**: 모바일 스캔 OCR이 기기→Gemini 직접 호출(`EXPO_PUBLIC_GEMINI_API_KEY`), eas.json에 env 미정의 → 프로덕션 APK에서 스캔 전체가 "키 없음"으로 죽을 수 있음. 반대로 키를 넣으면 APK에서 추출 가능 = 서버 예산캡 우회 과금 경로. 웹 API 경유(thin client 원칙)로 교체 권장.
3. **hair-v2 랜덤 매칭 수치**: `skinToneMatch = 75 + random(15)` (hair-v2/route.ts:209) — "같은 사진이면 같은 결과" 서사와 정면 모순. 결정론 값으로 교체.
4. **proxy.ts 임시 `/dev(.*)` 공개 라우트** — "커밋 전 제거" 주석과 함께 워킹트리 잔존. 현 브랜치 커밋 전 제거.

**🟠 리스팅 문구 반영 완료**

- **스캔 문구 교체됨(전 언어)**: 모바일 스캔의 실물은 "제품 어울려?" 사진 판정이 아니라 **성분표 OCR → 성분×피부 적합도**. "이거 나한테 어울려?" 프레임 → "성분 스캔" 프레임으로 수정. (옷 사진 어울림 판정은 웹 코치 채팅에 있으나 모바일 미확인이라 클레임 제외.)
- **"12타입·나만의 팔레트"는 조건부**: 서버는 12톤 판정 + 개인화 palette를 주지만, **모바일 결과 화면은 4계절 하드코딩 팔레트로 표시하고 서버 palette를 버림**. 기존 ColorPalette 컴포넌트 재사용으로 저비용 수리 가능 — 수리 없이 제출하면 "12타입" → "웜톤·쿨톤 타입"으로 완화 필요. 개인화 팔레트는 현재 홈 브리핑에서만 노출.
- **재현성 클레임은 설계 목표이지 하드 보장 아님**: Lab 결정론 분류기·temperature 0.1~0.3·prior tie-break·모델 고정은 실재하나 Gemini 추출 단계가 확률적이고 이미지 해시 캐싱은 없음. 실기기 스모크에서 동일 사진 반복 검증 후 흔들리면 "결과가 흔들리지 않도록 설계했어요" 수준으로 완화.
